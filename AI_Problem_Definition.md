# AI Problem Design: Student Query Classification System

**Prepared for:** SWYNEX — Task 1: AI Problem Design  
**Project type:** Narrow NLP classification prototype  
**Status:** Problem definition and reproducible baseline project

## 1. Problem statement
College support teams receive student questions about academics, fee payments, student accounts, scholarships, and general services. Manually forwarding each message to the right team can take time. This project explores a narrow AI use case: classify a short student query into one of five predefined support categories so that a staff member can route it appropriately.

**Input:** one short text query from a student.  
**Output:** one category label: `Academics`, `Fees`, `Account`, `Scholarship`, or `General`.

The prototype classifies queries only. It does not answer students, make decisions about scholarship eligibility, process payments, or replace staff.

## 2. Target users
- **Primary users:** college helpdesk operators and student-support/admin staff who triage incoming messages.
- **Indirect users:** students whose queries need to reach the correct team.
- **Out of scope:** automated handling of sensitive cases, emergency support, financial decisions, and official academic advice.

## 3. Data source and handling
For the initial prototype, the project uses a small, manually labelled **synthetic demonstration dataset** included as `data/student_queries.csv`. It contains example queries written for this project, not real student messages. No real names, student IDs, phone numbers, financial records, or other personal data are included.

The CSV has two columns:
- `query`: short student-support message
- `label`: expected category assigned for supervised learning

This is a starter dataset for testing the pipeline, not evidence of real-world performance. Before deployment, it would need to be replaced or supplemented with appropriately consented, anonymised, representative queries labelled by knowledgeable reviewers.

## 4. Narrow AI approach
A lightweight supervised text-classification pipeline is proposed:

`Query text → TF-IDF text features → Logistic Regression → Predicted category`

- **TF-IDF** converts words and short word combinations into numerical features.
- **Logistic Regression** learns associations between those features and the category labels.
- A fixed random seed and stratified train/test split support repeatability.
- The code reports test accuracy, macro precision, macro recall, macro F1, a classification report, and a confusion matrix.

This is a baseline chosen for interpretability and low compute requirements. It does not require a GPU.

## 5. Evaluation approach
The script uses an 80/20 stratified train/test split. The test portion is held out from model fitting. Run:

```bash
python -m pip install -r requirements.txt
python src/train_evaluate.py
```

The program prints:
- **Accuracy:** fraction of test examples classified correctly.
- **Macro precision / recall / F1:** averages the metric across categories so each category contributes equally.
- **Per-category report and confusion matrix:** helps reveal categories that are confused with one another.

### Success targets (targets, not claimed results)
- Test accuracy of at least **85%**
- Macro F1-score of at least **0.80**

These are evaluation targets only. The actual results must be generated by running the script and should be reported honestly. Because the included dataset is synthetic and small, results on it must not be presented as proof of production readiness.

## 6. Constraints and risks
1. **Small synthetic dataset:** patterns may be too simple and may not represent how students actually write.
2. **Limited labels:** only five categories are supported; out-of-scope queries may be forced into an incorrect category.
3. **Language limitation:** initial examples are in English; Hinglish, Hindi, spelling mistakes, and code-switching may reduce performance.
4. **Ambiguity:** some queries can fit more than one department.
5. **Dataset bias / leakage:** very similar examples across training and testing can inflate metrics. A future evaluation should use a larger, independently collected test set and check near-duplicates.
6. **Privacy:** real deployment would require data minimisation, access controls, retention rules, and review of consent/legal requirements.
7. **Human oversight:** low-confidence or ambiguous predictions should be sent to a human rather than automatically routed.

## 7. Human-in-the-loop behaviour
This baseline is a research/demo classifier. In a real support workflow, the model should provide a suggested category, and staff should be able to correct it. A confidence threshold and an `Other / Needs review` pathway should be added before any real-world use.

## 8. Limitations
- It predicts a category; it does not answer questions.
- It does not yet have a calibrated confidence threshold or unknown-class detector.
- It has not been validated on real college messages.
- Its performance may change significantly with new institutions, writing styles, languages, or category definitions.

## 9. Next steps
1. Ask domain reviewers to refine category definitions and label examples.
2. Collect consented, anonymised, representative queries.
3. Create a separate evaluation set and check for duplicates.
4. Compare Logistic Regression with a simple baseline and other appropriate models.
5. Review errors by category and language.
6. Add a human review path before any pilot.

## 10. Expected output example
**Query:** “I forgot my student portal password. How can I reset it?”  
**Expected category:** `Account`

**Query:** “When is the last date to pay semester fees?”  
**Expected category:** `Fees`

## 11. Responsible-use statement
This prototype is intended to demonstrate a narrow AI workflow. It should not be used to make consequential decisions or to automatically reject, prioritise, or resolve student requests. A human remains responsible for reviewing and routing messages.
